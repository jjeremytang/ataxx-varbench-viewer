## 1. Authority hierarchy

當文件或程式敘述互相衝突時，依下列順序判定：

1. `SPEC.md`：目前全域規格與版本規則。
2. 已凍結的 experiment protocol：該次正式實驗的實驗條件；產生 outcome 後視為 immutable。
3. machine-readable manifests / SHA-256：實際資料與 artifact provenance。
4. `PROJECT_STATUS.md`：目前 Current Task、狀態與下一步。
5. `PROJECT.md`：研究方向與方法概覽，不保存細部 runtime constants。
6. README / logs：導覽與歷史紀錄，不作為規格來源。

Machine-readable mirror：`spec/project_spec.json`。

## 3. Ataxx rule semantics

Authoritative human-readable rule description：`RULES.md`。

Current engine invariants：

- minimum board size: 4;
- Red first, Blue second;
- Chebyshev distance 1 = Clone，distance 2 = Jump;
- move 後目的格相鄰距離 1 的敵棋全部轉色；
- forced Pass only when no legal normal move exists;
- terminal if either color has zero pieces, no Empty square remains, two consecutive passes occur, or the same complete state repeats;
- repetition state key includes board, side to move, consecutive-pass count;
- repetition terminates as draw。

Primary research board：standard `7×7`、0 obstacles。Procedural `N×N` / obstacle boards 是 extension，不是目前 V3/V4 claim domain。

## 4. Search semantics

Current authoritative search implementation：`SearchEngine` in `include/search.hpp` / `src/search.cpp`。

- fixed-depth Alpha-Beta；
- non-terminal evaluation = root-player piece difference；
- terminal win/loss uses `WIN_SCORE` plus/minus piece difference；
- repetition evaluates as draw (`0`)；
- deterministic internal move ordering；
- root tie-breaking follows legal-move generation order；
- each `SearchEngine::search` call has fresh node counter；
- V3/V4 d2/d4/d6 measurements are independent calls unless a later protocol explicitly introduces tree reuse。

`d6` is a deeper reference, not ground truth or perfect play。Iterative Deepening is not part of the current formal baseline。

## 7. V4-01 position-level selective deepening

Frozen protocol：`docs/v4_01_position_selective_deepening_protocol.md`。

Primary `PSV-20`：always d4；within ply 6–30 also compute locked detector inputs；if score ≥ fixed threshold `0.500931073443522`, run d6 and adopt d6 move。

Threshold SHA-256：`641d568427e36cd3cb893fbe5d495f6e3596019f5451e433e84d2aff60d32f52`。Opening SHA-256：`9ed4bf2c1137e2a6f61a3386a021514f85cca9988072c0580e0bff2802dcba49`。

Verified primary result：PSV-20 vs P4 score rate **59.0%**；PSV/P4 nodes **6.40×**；PSV/P6 nodes **13.37%**。This supports improvement over fixed d4 at much lower cost than d6, not near-d6 playing strength。

## 9. V4-06 hardened protocol

Authoritative task protocol：`spec/v4_06_conversion_analysis.json`，schema `2`，feature semantics `v4-06-features-2`。

### 9.1 Unit / outcome / leakage rule

Primary unit is a validated oracle-replay eligible state。Primary root branch is **only `original_d4_move`**。Retrospective outcome is `oracle_move_changed_4_6 = 1 iff original_d4_move != replay_d6_move`。

`replay_d6_move`、d6 score、label 或任何 d6-derived quantity may define outcome only；they must not choose a branch or enter an online conversion rule。

### 9.2 Conversion metrics

For root move `m`：

- `I(m)` = immediate converted enemy count；
- `C(m)` = maximum immediate conversion available to an opponent reply after `m`；
- `S(m)=I(m)+C(m)`；
- `B(m)=I(m)-C(m)`；
- material gain `G=2k+1[Clone]`；
- `A2=G0+G1` = two-ply material amplitude；
- `N2=G0-G1` = two-ply net material balance；
- maximum opponent infection hotspot on `board_before`；
- deterministic conversion cascade `k0+k1+k2` and material amplitude `G0+G1+G2`。

Deterministic continuation uses maximum immediate conversion, then material swing, then canonical move text as tie-break。It is a mechanism descriptor, not optimal play。

### 9.3 Required cohorts and phase control

Every development analysis must report：

1. all eligible states；
2. detector-negative states (`original_deepened=0`) separately, where unstable rows are missed instability；
3. pooled plus early / mid / late stratification for both cohorts。

A pooled association alone is insufficient because conversion opportunity and instability may both vary with ply/phase。

### 9.4 Uncertainty

Primary interval = **opening-seed clustered bootstrap 95% percentile CI**；bootstrap unit = `opening_seed`；2000 replicates；fixed RNG seed `20260827`。Wilson intervals are descriptive secondary intervals only。

### 9.5 Fresh confirmation gate

Development uses opening seeds `202608250001–202608250100` retrospectively。Reserved fresh seeds are `202608250101–202608250150` and may not be used for tuning。

Fresh confirmation requires all of：

- an explicitly frozen `spec/v4_06_frozen_rule.json`；
- its SHA-256 registered in `spec/project_spec.json`；
- project validator PASS；
- an authoritative validated replay source for reserved seeds。

A manual confirmation checkbox is not a scientific gate and is not accepted。

## 10. Seed Spec policy

New Master Seeds use Seed Spec v3。v2 is decode/replay compatibility only。C++ and public Viewer JavaScript must share fixed known-vector tests。

## 11. Program / workflow status policy

Programs are classified as `authoritative-current`, `experiment-frozen`, `utility-current`, `legacy-pilot`, or `one-time-archive`。Detailed mapping：`docs/code_registry.md`。

The exact active `.github/workflows/*.yml` set is registered in `spec/project_spec.json` and machine-checked by `tools/validate_project_spec.py` to prevent documentation drift。

## 12. Output schema, provenance, and archival rule

Every new formal artifact must record：

- project/spec version；
- task schema / feature semantics version；
- source commit / runner provenance；
- board/rule/search configuration；
- relevant frozen artifact SHA-256 values；
- data class；
- validator status。

GitHub Actions artifacts are **transport copies**, not the sole long-term record。Before a formal task is marked verified-complete, its validated evidence must be archived under the task's `results/` path (V4-06：`results/v4_06/`) with source manifest and SHA-256 checksums。

## 13. Change-control rule

A change is semantic if it can alter game states, legal moves, search scores, best-move tie-breaking, detector scores, gating decisions, sampling distribution, feature definitions, statistical interpretation, or outcome interpretation。

Semantic changes require：

`PLAN → IMPLEMENT → VERIFY → new protocol/schema version → RUN`

Completed frozen raw outcomes are never rewritten merely to add fields；supplemental data must be a derived artifact with provenance。
